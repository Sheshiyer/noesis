# Shared identity client integration

Implemented source on 7 November 2026. No extension publication or backend deployment performed.

Account uses Raycast OAuth.PKCEClient with RedirectMethod.Web, client ID `noesis-raycast`, and the actual `authorizationRequest.redirectURI` in code exchange. Register exactly `https://raycast.com/redirect?packageName=noesis` based on package name and [Raycast's OAuth documentation](https://developers.raycast.com/api-reference/oauth). Observe the emitted callback during a real Raycast sign-in before production acceptance; a build cannot establish native callback behavior.

Tokens reside in Raycast's secure OAuth token store, partitioned by API origin. Refresh and revoke share a filesystem lock across extension command processes, reread tokens under lock, and fail closed on timeout. An orphaned `session-<origin hash>.lock` requires operator inspection after confirming no command is executing; it is not automatically stolen. Account generation rejects in-flight responses after sign-out or replacement. Sign-out revokes first; on network failure it retains credentials so revocation can be retried. Raycast's own automatic OAuth logout removes tokens locally; only the Account command performs the server revoke call.

Account retrieves current allowed subject and independent relationship grants, shows verified preferred email, reads qualified subject profiles, saves with expected revision and fresh edit grants, and persists the shared default subject. Read-only subjects cannot save. Account profiles are retrieved live; private cache paths and local draft keys include origin/account/subject. Guest defaults stay local and are not imported. The API-key command remains a distinct operator mode. General profile PATCH no longer sends email.

Account now starts preferred-email linking through POST /account/email-links, validates the returned verification URL against the fixed HTTPS API origin and exact verification path, opens the browser, and requires fresh sign-in plus preferred-email readback before success. Account subject actions support POST /subjects/:id/engines/:engine_id/calculate with only expected_revision, explicit options and optional current_time, plus subject-scoped reading list/detail. Calculation requires can_calculate=true; read/edit grants do not substitute. The server loads accepted birth inputs. Generic operator commands remain distinct; human workflows remain held until a subject-scoped workflow endpoint exists. Relationship rows reflect allowed resources only; joint report bytes need the finalized reader endpoint. Existing operator engine adapters and user input forms remain available. Native UI, real OAuth callback, refresh rotation, revocation, grant matrix, and cross-surface persistence require actual signed-in acceptance after backend rollout.
